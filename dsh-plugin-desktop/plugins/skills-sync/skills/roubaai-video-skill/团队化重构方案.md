# roubaai-video-skill 团队化重构方案（基于 dsh-agent-teams）

> 状态：方案稿 v0.3（v0.2 基础上修正：读取策略改为「分层按需、禁止一次全读」；全部 references 文件名按磁盘实存校正）
> 形态：A 动态组队 —— 改写 `SKILL.md` 为 captain 协议，用户仍用「使用 roubaai-video-skill …」即自动拉起团队
> 运行时：dsh-agent-teams（已激活 `@nanmicoder/dsh-agent-teams@0.1.16-rc.1`，`agent_teams_*` 工具就绪）

---

## 0. 目标与前提

**目标**：把当前「主 agent 串行写全部 01–10 模块」重构为「captain + 专职 member 团队」，
让每个专科由专注的 sub-agent 深度处理，靠 task 依赖 DAG 推进、靠 quality gate 做每阶段审核，
直接解决「主 agent 做全部 → 上下文稀释 → 质量差」的问题。

**已确认前提**：
- agent-teams plugin 已在 web profile 的 bundle 列表（`package.json` 含 `@nanmicoder/dsh-agent-teams`），`agent_teams_*` 工具对所有 session 可用。
- roubaai-video-skill 已在 `dsh-home/skills/roubaai-video-skill`，44 个 `references/` 完整。
- roubaai 已有 `.assets/<项目名>/` 状态保持机制（文本落盘 + 媒体资产单源），可直接复用作 member 间产物传递。

**不改动**：`references/` 全部专科规则保持单一真相源；现有「阶段交接」「平台节奏档案」「红线」作为 captain 编排约束保留。

**质量侧重点（作者经验，贯穿全链路）**：
- **文字类**（01/01b/02/03）：故事是否足够吸引人、是否用「人话」写、AI 感不能重。写剧本亦然。文字类先读 `09-humanizer-zh.md` 学怎么写人话。
- **图片类**（05）：尤其是真人类，先读 `05-anti-ai-realism.md` 学怎么作图，避免油腻/塑料/假。
- **提示词类**（06）：**重中之重**，必须审核到位，作为全流水线最严门禁。

## 1. 总体架构

```
用户: 使用 roubaai-video-skill，开发竖屏短剧项目
        │
        ▼
主 agent 变为 CAPTAIN（roubaai SKILL.md 改造后的协议）
        │  ① 判断项目所处阶段 / 最早缺失环节
        │  ② agent_teams_create            → 建队
        │  ③ agent_teams_add_member × N    → 拉专职 member（persona 见 §2）
        │  ④ agent_teams_create_task × M   → 拆 DAG（见 §3）
        │  ⑤ 监控 agent_teams_status        → 推进 / 处理 halted
        │  ⑥ 汇总各 member 产物 → 汇报      → agent_teams_delete 归档
        ▼
专职 members（continuable sub-agents，各持完整 fs/bash/web 工具）
   chief-writer / art-director / storyboard-director /
   prompt-engineer / sound-designer / editor (+ reviewer)
        │  每个 member 开工前读取对应 references/（单一知识源，见 §7）
        ▼
产物落盘 .assets/<项目名>/ ，下游 member 被 task 依赖唤醒后从磁盘续接
```

### 2.1 chief-writer（编剧总监）
```
name: chief-writer
role: |
  你是中文影视编剧总监，负责 roubaai 流水线的「剧本」全段：
  项目开发(01)、完整剧本写作(01b)、剧本医生会诊(02)、台词专家(03)。
  读取策略（分层按需，不要一次全读，见 §7）：
  · 常驻地基（每次开工必读）：09-humanizer-zh.md —— 先学「怎么写人话」，再动笔
    （首次读全文；后续 task 只需 Grep 定位其中的「AI 模式诊断 / 自检清单」章节重读，省上下文）
  · 按当前 task 读对应文件（只读正在做的那一阶段，其余不读）：
      01  项目开发        → 01-script-creation.md
      01b 完整剧本写作    → 01b-script-drafting.md
                            （按需加：01b-rhythm-matrix / startup-triggers / modes-format /
                              workflow-output / boundary-examples）
      02  剧本医生会诊    → 02-script-doctor.md
                            （按需加：02-panels-examples / startup-workflow /
                              boundary-interface / rules-granularity-output）
      03  台词专家        → 03-dialogue-expert.md
  以上均位于 {SKILLS_ROOT}/roubaai-video-skill/references/
  严格按上述文件的结构、红线、自检与输出格式工作；不擅自改剧情主体时只做会诊/精修。
  所有文字产出（logline/大纲/剧本/台词）落盘前必须做「人话 / 吸引力 / AI感」三问自检：
    · 是否像人在说话，而非模板腔/翻译腔/书面腔；
    · 是否有足够钩子与信息增量，能否吸引人追读；
    · 是否规避明显 AI 痕迹（对照 09-humanizer-zh.md 的 AI 模式诊断项）。
  默认中文输出。短视频平台项目必须先建/继承「平台节奏档案」（见使用手册 §5）。
  产出写盘：.assets/<项目>/剧本/（含 logline、大纲、项目档案、完整剧本、会诊报告、台词卡）。
  若文件不可读，停止并 send_message 给 captain 说明。
```

### 2.4 prompt-engineer（提示词工程师）
```
name: prompt-engineer
role: |
  你是视频生成提示词工程师，负责 roubaai 流水线 06 提示词书写与调参（专注，不写剧本/不分镜）。
  读取策略（分层按需，不要一次全读，见 §7）：
  · 主文件（写提示词时按需 Grep 定位章节读，禁止整读）：
      06-core-format.md（78KB，提示词核心格式与规则）
  · 按当前需要加读：
      出错/要排查问题  → 06-diagnostics.md（25KB）
      连续性资产复用    → 06-continuity-assets.md（17KB）
      高阶导演技法      → 06-advanced-director.md（13KB）
  · 按实际生成模型二选一（不要两个都读）：
      Seedance 2.0  → 06-seedance2-adapter.md（22KB）
      Seedance 2.5  → 06-seedance25-adapter.md（13KB）
  以上均位于 {SKILLS_ROOT}/roubaai-video-skill/references/
  · 严格使用「全文一致」提示词 + 全局 ST/CL/NP 风格锁展开；
  · 素材名必须与 ./assets 中的文件精确一致（@图N 映射核对，防漂移）；
  · 核心概念/长句、冲突、停顿、字数、标点按阶段规则走；时长参数输出到 .assets；
  ★★ 写作标准：动笔前先加载，按标准写（你是第一责任人，reviewer 只复核，不要写完再改）★★
  · ① 抽象转译：抽象 / 心理 / 文学描写必须转成可拍微动作。
      反例：后怕、杀意一闪、心如死灰
      正例：「后怕」→ 肩头一颤、打寒噤、拳指收拢；「杀意一闪」→ 眼底一冷 → 随即掩去 → 眨一下收住
  · ② 光影 8 项（每单元逐项写全）：光源来源与方向 / 主光与辅光 / 亮区 / 暗区 /
      脸部受光 / 轮廓光或背景分离 / 色温 / 明暗反差
      禁用空泛词：电影级布光 / 高级光影 / 氛围感
  · ③ 表演 7 项：眼神 / 眨眼 / 嘴部 / 呼吸 / 肩颈 / 手部 / 身体重心
      主演主情绪镜 → 全写全，不许省略；豁免（如剪影长卷）→ 必须注明理由；
      副角 / 背影 / 特写 / 快动作镜 → 可按构图省略
  · ④ 限制三不：每单元写全「保持 + 禁止 + 不要」三段，并叠加反过度表演
      （不要假哭 / 夸张皱眉 / 大喊 / 情绪失控，除非剧本明确爆发）
  · ⑤ 字数闸门 + 镜头数（**唯一闸门是 1900 字，不是镜头数**）：
      正常写，**镜头数不设限**（一个单元写 4 个、5 个分镜都可以）
      只有「超过 1900 字」才拆分：按分镜边界拆，每单元约 3 个分镜，**不删减提示词内容**
      未超 1900 字就不必拆
      @图片N 每单元 1–4 张，单组 ≤9 张
  · 超字数处理（>1900 时按序执行，禁止靠删画面细节压字数）：
      1) 删管理话术 / 重复限制 / 空泛形容词（无损）
      2) 改 C 导演轨 + 静态信息交给 @图N，提示词只写本镜变化
      3) 换 Seedance 2.5 的 30s 大分镜
      4) 按镜头边界拆连续单元，用「段末状态」承接下一单元第一帧
      禁止删：人物锚定 / 景深焦点锁 / 摄影机行为锁 / 台词与语气 / 可执行光影 / 段末状态 / 功能镜头
  · 每个单元落盘时必须附「自检表」：5 项逐项打勾 + 字数实测值，供 reviewer 复核
  产出写盘：.assets/<项目>/提示词/（每批 prompt 卡，含参数与时长、自检表）。
  依赖：读取 t-asset 的资产库 + t-board 的 shot 列表。
```

### 5.1 提示词审查清单（hard checklist，5 项全 ✓ 才放行）

> ⚠ **双份维护说明**：member 是 sub-agent，拿不到本方案文件，只能看到自己的 persona 文本。
> 因此本清单在 **§2.4 prompt-engineer 的 persona 内有「内联执行版」**，内容必须与本清单一致；
> 改任何一处必须同步另一处。（更彻底的单一真相源解法见 §8 待确认点 6）
>
> 提示词是全流水线质量核心：提示词一错，后面生成的素材全废。
> prompt-engineer 落盘前自检、reviewer 放行前复核，**都按这 5 项逐项打勾，任一不过即 `needs_revision`**。

**① 抽象转译 ✓**
所有抽象 / 心理 / 文学描写必须转成**可拍微动作**，不得把情绪词直接丢给模型。
- 反例：`后怕`、`杀意一闪`、`心如死灰`
- 正例（保留为范式）：
  - B04c「后怕」→ `肩头一颤、打寒噤、拳指收拢`
  - B05a「杀意一闪」→ `眼底一冷 → 随即掩去 → 眨一下收住`
- 案例库：更多「抽象 → 微动作」转译范式见 `04-appendices.md`（Grep 定位，勿整读）
- 判定：出现未拆解的情绪/心理/文学性抽象词 → 不合格。

**② 光影 8 项 ✓**
每个单元**逐项写全**，全片所有单元一致（脚本校验 8 项全 ✓）。
8 项：光源来源与方向 / 主光与辅光 / 亮区 / 暗区 / 脸部受光 / 轮廓光或背景分离 / 色温 / 明暗反差
- 出处：`04-core-workflow.md`（光影可执行规则）+ `04-field-methods.md`（光影字段自检）
- 禁止：`电影级布光`、`高级光影`、`氛围感` 这类空泛词
- 判定：脚本校验 8 项未全 ✓ → 不合格。

**③ 表演 7 项 ✓**
7 项：眼神 / 眨眼 / 嘴部 / 呼吸 / 肩颈 / 手部 / 身体重心（出处 `04-core-workflow.md` 情绪拆表演过程）
- **主演主情绪镜**：7 项**全写全，不允许省略**
- **可豁免**：仅限构图本身不呈现表演的镜头（如 B04b 剪影长卷），**必须写明豁免理由**
- **可合理省略**：副角 / 背影 / 特写 / 快动作镜，按构图判断，审查时须点名确认
- 判定：主演主情绪镜缺项、或豁免未注明理由 → 不合格。

**④ 限制三不 ✓**
每个单元写全三段：**保持** + **禁止** + **不要**，并叠加**反过度表演**约束。全片所有单元（本例 13/13）全 ✓。
- 反过度表演范式：不要假哭、不要夸张皱眉、不要大喊、不要情绪失控（除非剧本明确爆发）
- 无人群需求另需写 `不允许出现额外人物、路人、群演`
- 判定：三段任缺其一、或缺反过度表演 → 不合格。

**⑤ 字数图数 ✓**
- 字数（**上限性质已校正：1900 不是 Seedance 平台限制**，详见 §5.3）：
  | 档位 | 字数 | 说明 |
  |---|---|---|
  | **正常交付** | ≤1900 字 | 正常写，**镜头数不设限**，不必刻意压短 |
  | **红线** | >1900 字 | 才需要按 §5.2 压缩或拆分（按分镜边界拆，每单元约 3 镜，**不删内容**） |
- 图数：`@图片N` 每单元 1–4 张，**单组上限 9 张**
- 超限处理：按 §5.2「超字数无损处理 SOP」执行，**不得靠删画面细节压字数**
- 判定：>1900 未按 SOP 处理、或超图数闸门 → 不合格。

### 5.2 超字数无损处理 SOP（触发 >1900 时按序执行）

> 核心原则：**压字数绝不靠删画面细节**。
> 先删零信息量内容 → 再换更省字的格式 → 最后拆段（拆段是分次生成，不是删内容）。
> 出处：`06-core-format.md`（1900 安全线 / 强度保护 / 压缩顺序 / 镜头密度保护）、
> `06-continuity-assets.md`（1900 安全红线策略）、`06-seedance25-adapter.md`（2.5 切片与闸门）。

**Step 1｜无损清理（按序执行，删的都是本来就没信息量的）**
1. 管理话术、解释说明（如「接下一大分镜」「本段为…」）
2. 默认不输出的低收益后缀项
3. 合并重复限制（同一约束在多处重复写）
4. 缩短空泛形容词（「电影级」「高级」「氛围感」）
5. 缩短非末镜的可见转接
6. 把同一控制点集中到 `硬锁 / 声音轨 / 段末状态`
7. 用**更短但完整**的摄影机行为句、光影句表达同一控制

**Step 2｜换更省字的格式（不减信息）**
- 改用 **C 导演轨纯净版**：字段合并进镜头轨，把字数留给镜头轨的关键控制
- **静态信息交给参考图**：角色外观、场景结构由 `@图N` 承担，提示词只写「本镜的变化」，
  不重复描述图里已有的信息（结构性减负，画面信息不丢）

**Step 3｜换更宽的容器**
- 信息密度确实高时，改用 **Seedance 2.5 的 30s 大分镜**（全局设定 + 时间戳切片剧本），
  单段可容纳更多切片（2.0 为 4–15s，2.5 为 4–30s）

**Step 4｜拆段兜底（不删内容，分次生成）**
- 拆分点必须落在**镜头之间**（2.5 按切片边界），**不得在单个镜头内部硬拆**
- 用上一单元 `段末状态` 承接下一单元第一帧
- 拆成连续单元后，每个单元仍需各自通过 §5.1 五项审查
- 台词导致的超限：按**台词节拍**拆连续单元，或回 03 精修台词；**不得靠加快语速硬塞**

**红线｜以下一律禁止删除或压扁（删了就是损失画面细节）**
素材用途与人物锚定 · 场景与人物位置关系 · 景深与焦点锁 · 摄影机行为锁 · 台词与语气 ·
可执行光影 · 段末状态 · 命中的 CR / FF / MAP / SB / SCV / PR / 视频延长约束 ·
功能镜头（动作标点、道具信息、反应镜头、段末钩子）

**镜头密度保护**
不得为压字数把「短视频中高密度」「高密度动作或强钩子」压回 1–2 镜；
密度合格后若仍超限，走 Step 4 拆段，**不删功能镜头**。

### 5.3 镜头数 × 提示词长度的权衡（注意力预算）

**一、官方事实（已校正 —— 此前「2000 是平台硬上限」的说法错误）**

| 项 | Seedance 2.0 | Seedance 2.5 |
|---|---|---|
| 最大边界 | 约 **5000 字符** | 控制台 **15000 字**；**API 侧无硬性上限** |
| 推荐长度 | **≤500 字** | — |
| 官方说明 | 内容过长会受**注意力机制限制**，可能导致**细节丢失和逻辑弱化**；控制在建议长度内可获得更稳定、更优质的生成效果 | — |
| 计费 | **与 prompt 文本长度无关**：文本 / 图片 / 音频不计入 token 且不收费；**只有视频按时长计 token** | 同左 |

> 结论：**1900 / 2000 不是 Seedance 的限制，2000 通常是三方平台的限制。**
> 1900 是本流水线出于**注意力保护**设的自律红线（远低于 5000 字符边界）。
> 注意：不要据此反向追求短提示词或刻意少放镜头——**闸门只有一个：1900 字**。
> 正常写、写完不超 1900 就交付；超了才拆。

**二、核心矛盾**
单元容量固定，**「镜头数 × 每镜细节深度」= 容量**。
镜头多 → 每镜分到的字少 → 细节被压 → 生成质量掉；长提示词本身还叠加注意力衰减。

**三、量化基准**

| 单单元字数 | 可容纳镜头数 | 每镜可写字数 | 能否写满 |
|---|---|---|---|
| 单单元字数 | 该单元镜头数 | 每镜可写字数 | 能否写满 |
|---|---|---|---|
| 1900 字 | 3 镜 | ~630 | 写得满 |
| 1900 字 | 4–7 镜 | 270–475 | **装不下，必然压细节** |

→ 06 现有规则「C 导演轨默认 4-7 镜、高密度 8-10 镜」与「每镜写全」在字数上**无法同时成立**。

**四、权衡原则：宁可多拆单元，不可压缩每镜细节**
- **拆单元几乎不增加成本**：文本不计费，视频按**总时长**计费，总时长不变则成本基本不变
- **压细节的成本**：画面质量直接下降，且不可逆

**五、分档执行**

| 档位 | 每单元镜头数 | 字数 | 每镜写法 | 适用 |
|---|---|---|---|---|
| **常规**（默认） | **不设限** | ≤1900 字 | 光影 8 项 + 表演 7 项 + 三不 全展开 | 绝大多数段落 |
| **快切** | **不设限** | ≤1900 字 | 每镜只写变化量（构图 + 动作 + 光影关键点） | 纯节奏快切，无需细腻表演 |

> ⚠ **唯一闸门是 1900 字，不是镜头数。**
> 正常写即可——**写了 4 个或 5 个分镜、按规范写完后仍不超过 1900 字，就不必拆**。
> 只有**超过 1900 字**才拆分；拆分时按每单元约 3 个分镜分组，**不删减提示词内容**。

**六、决策顺序**
1. 按 04 的节奏档位表确定叙事需要的镜头数，**正常写完**（镜头数不设限）
2. 估算字数：**≤1900 → 直接交付，不拆**
3. **>1900 → 才拆**：按分镜边界拆，每单元约 3 个分镜，**不删减内容**
4. 单元之间用 `段末状态` 承接
5. 拆分后每个单元仍需各自通过 §5.1 五项审查

> ⚠ **拆单元 ≠ 减镜头**：叙事要求的总镜头数不变，变的只是投喂批次。

**门禁原则**：
- reviewer 是**独立**角色，不创作、只审查，出具 `verdict=pass / needs_revision` 并附至少一条 finding。
- 提示词门禁是**重中之重**——提示词一错，后面生成的素材全废，所以它的审核强度最高。
- 任一门禁未过，下游 task **不得**开始（captain 负责拦）。

## 10. 风险与取舍

| 风险 | 取舍 |
|---|---|
| 多 agent 带来多倍 token 成本 | 接受：换质量；先小项目实测成本再决定规模 |
| member 读不到 references 导致凭记忆硬写 | 用「读不到就停下报 captain」的硬约束兜住 |
| DAG 依赖配置错导致下游空跑 | 门禁拦截 + captain 阶段判定从最早缺失环节续接 |
| 团队化后流程变复杂，简单项目也走全套 | captain 按需要**部分拉队**（可只拉 2–3 个 member），不强制全阵容 |
| 与现有单 agent 流程不兼容 | 过渡期保留备份的旧 `SKILL.md`，可回退 |
